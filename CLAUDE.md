# Stock Alerts

Stock alert system that screens tickers by fundamentals and spots opportunities through two rules: current price vs. the analysts' price target (`AnalystAlerts`) and price drops over several time windows (`PriceAlert`). It runs daily at 14:00 (mainland Spain time) via GitHub Actions.

## How to run

```bash
# Backend: from the repo root, with the venv active
cd src && python main.py
```

```bash
# Frontend: generate the data first with the command above
npm --prefix web install && npm --prefix web run dev
```

The GitHub Actions workflow runs `python main.py` with `working-directory: src`, so every import is relative to `src/`.

`requirements.txt` is pinned by hand. The pre-commit hook (`tools/check_requirements.py`) only checks that the package names match the imports in `src/`, and fails naming what is missing or unused; it never rewrites versions.

## Functional requirements

**`docs/requirements.md` is the source of truth for WHAT the application does**: thresholds, windows, pages, filters, defaults, ordering, the email. This file only covers HOW it is built. **Keep it up to date**: any change that alters behaviour visible to the user -- a threshold, a filter, a default, a page, a column in the email -- must update `docs/requirements.md` in the same change. When the code and that file disagree, ask which one is right rather than silently following either.

## Architecture

- **Hexagonal**: `providers/base.py` defines the `DataProvider` interface (ABC). `YFinanceProvider` is the concrete adapter. `DataProviderImpl` composes the adapters and adds loading tickers from JSON.
- **One source, N sinks**: `pipeline.run_pipeline()` computes and returns a `Snapshot` (a dataclass with `screened`, `analyst_alerts`, `price_alerts`) with no side effects. Consumers format it: `notifications/` into text for the email, `export/` into JSON for the web.
- **Alerts return data, not text**: `BaseAlert.run()` returns a `DataFrame` enriched with `short_name`. Subclasses implement `compute()` (the rule's numbers for every ticker) and `apply_rules()` (the rows that trigger). No formatting inside `alerts/`.
- **The rules are computed for the whole universe; only screened stocks alert**: Search filters every stock, screened or not, so `run_pipeline()` downloads prices, analyst targets, quarterly statements and EPS inputs for all ~540 tickers and runs both rules on all of them (`analyst_all`, `price_all`, on `Snapshot.universe`). `analyst_alerts` / `price_alerts` are then narrowed to the screened stocks (and the funds, for the price rule): the screener still decides what is worth an email, an LLM call or a card on the alert pages. `companies.json` has one row per stock of the universe and per fund, with `screened`, `analyst_alert` and `price_alert` flags; the alert pages keep only the rows that fired. `DEFAULT_TICKER_LIMIT` in `pipeline.py` is `None` (about 220 tickers pass today); a number there caps the screened list for a quicker local run.
- **Both rules describe every company**: `run_all()` returns the unfiltered table, and the cards take their numbers from it. A ticker that only fired the price rule still has a gap to its analyst target -- it just was not wide enough to alert on.
- **Prices are downloaded once, for five years** (`PRICE_HISTORY_PERIOD` in `pipeline.py`): the price rule needs more than a year for its longest window, and the web chart offers a five-year view. Each `prices/<ticker>.json` carries every trading day of the last year and one point a week before that, which is all a 3-month view needs and a fifth of what five daily years would weigh. **One file per ticker, downloaded by the detail panel when it opens** (`CompanyDetail` in `CompanyCards.tsx`): for the whole universe a single file would be megabytes every page paid for and nobody looked at.
- **Main flow**: `main.py` → `run_pipeline()` → `export_json()` + (when there are alerts) `format_snapshot()` → `send_email()`.
- **The run archive** (`export/history_export.py`): every run is also written as Parquet, one file per table and day, under `history/`. The JSON export describes only today and is overwritten; this one never is. It exists because most of a run cannot be recovered later -- prices can be fetched again for any past date, but today's analyst price target, today's screened set and today's LLM commentary are point-in-time facts, and a day that is not archived is lost for good. Nothing reads it yet: it is written now so the history exists when a history view is built. Parquet because it is columnar and compressed, so a future reader can pull single columns out of years of runs without a backend. Every file starts with `snapshot_date` and `generated_at`, so a table across time is one glob: `history/analyst_alerts/*.parquet`. `runs/` gets a row on every run even when nothing fires, so a quiet day is never confused with a day the job did not run.
- **The archive lives on its own branch**: CI checks the orphan `data` branch out beside the code and points `HISTORY_DIR` at it, so the daily data commit never touches the code history. `history/` is gitignored on master.
- **Contract with the web**: every file in `web/public/data/` is `{"generated_at": <ISO>, "rows": [...]}`. The frontend depends on that shape, not on the Python code.
- **`companies.json`**: one row per alerted company, joining both alert tables so the web has a single card per company. A ticker that fired only one rule has nulls in the other rule's columns, and the UI greys them out. The join lives in `export/`, not in the browser.
- **Fundamentals come in two granularities**: the annual figures (`data/fundamentals.csv`) are what the screener filters on -- they are the audited ones -- and are cached for the whole universe in one file. The quarterly ones (`data/fundamentals_quarterly.csv`) exist only so a card can show the recent trend, so they are fetched for the screened tickers alone and the cache grows ticker by ticker. Both end up in the same long-form shape, with a `year` or a `period` ("2026Q2") column, and the web renders them with the same component.
- **Fundamentals travel on the `Snapshot`**: `run_pipeline()` fetches them once, hands them to the screener (which would otherwise fetch them again) and keeps them, so a sink can show WHY a company passed the filters, not just that it did. `companies.json` carries them per company as `fundamentals` (latest year), `fundamentals_history` (every year) and `fundamentals_quarterly` (every quarter). The metric list lives in `FUNDAMENTAL_FIELDS` in `export/json_export.py`.
- **The two price-based ratios are computed, not fetched** (`src/valuation.py`): a PER and a price/sales ratio need a PRICE, which no statement carries, so they cannot live in the fundamentals cache -- that file covers the whole universe and a price-derived number in it would be stale the next morning. They come in two flavours, for two different questions. The year-by-year series (`priceEarnings`, `priceToSales`) is each year's CLOSING price over that year's diluted EPS and revenue, computed in the pipeline where the five years of prices already are, and appended to the annual table so every sink sees two more metrics; it answers "is this cheap against its own history?". Today's pair (`trailing_pe`, `price_to_sales` on the `Snapshot`) is the last close of the price history over the last twelve months of the statements -- the trailing four quarters where the company files them, its most recent full year where it does not, which is what makes this work for the tickers that report twice a year. It belongs to no period and is the headline number on a card. **yfinance's ready-made `trailingPE` is deliberately not used**: it contradicts yfinance's own accounts for some tickers (AENA.MC: an `info` EPS of 6.07 against a 1.42 in the income statement, a PER of 4.3 where the plausible one is 18.5), and a number that disagrees with the price printed beside it is worse than one we can account for. The ingredients (`Diluted EPS`, `Diluted Average Shares`) are cached in `data/valuation_inputs.csv`, ticker by ticker, for the whole universe: Search filters on today's PER. **Neither ratio is computed per quarter**: a single quarter's earnings would put the PER at roughly four times its real value, so the quarterly table simply has no such row (`FundamentalsHistory` drops any metric that is null in every period).
- **Every exported row carries `sector` and `description`** from `data/tickers.csv`. `description` is Yahoo's own summary: it exists for every ticker, so the UI always has text to show when the LLM commentary is missing.
- **Alert commentary** (`src/enrichment/`), split by how fast the answer goes stale:
  - `commentary.py` writes `explanation` -- why TODAY's number looks like that. One call per alerted row, on every run, because a reason from last month is a wrong reason.
  - `profiles.py` writes the company profile -- what it does, its revenue sources, its moat, its competitors, its threats, its outlook. None of that changes between a Tuesday and a Wednesday, so it is cached as one JSON per ticker under `HISTORY_DIR/profiles/` (the `data` branch in CI, so it survives between runs) and re-asked only after `TTL_DAYS`, or when a section is added to `prompts.py` and the stored file lacks it.
  - **The six sections are ONE call, not six**: the free tier allows 20 requests a day, so six questions per company would mean three companies a day and a dashboard that takes a week to fill. The model is asked for JSON and the answer is split back into sections; an unreadable answer leaves the profile untouched, to be asked again next run.
  - The questions all live in `prompts.py`, and adding a section there plus a line in `PROFILE_SECTIONS` in `CompanyCards.tsx` is the whole job. A failed call leaves the field null rather than stopping the run.
- **The LLM answers are in Spanish, and nothing else is**: they are what the reader of the dashboard reads. Every label, heading and column name around them stays English, like the rest of the repository.
- **LLM calls go through `utils/llm.py`**: `ask()` wraps LiteLLM, so the provider is a model name (`gemini/...`, `ollama/...`) and no caller needs to know which one answers. It is also the one place that throttles: calls are spaced `LLM_MIN_INTERVAL` apart and a rate-limited one is waited out and retried, because a 429 turns into an empty cell and a run of empty cells into a blank dashboard.
- **The price windows are calendar time, measured from the LAST price**: `var_1w` ... `var_1y` compare the last row against the close of the last session on or before the same date that many weeks/months back; `var_1d` compares it against the previous session. At 14:00 in Spain the last row of a European ticker is today's session in progress and that of an American one is yesterday's close, so 1D is always the move since the previous close. Counting trading rows instead (as before 2026-10-31) made "1M" mean six weeks and "9M" more than a year. Thresholds live in `THRESHOLDS` in `price_alerts.py`.
- **Funds are a second universe, price rule only**: `data/funds.json` lists index ETFs. It lives outside `data/tickers/` on purpose -- a fund has no statements, so mixed into the stock universe the screener would discard it. `run_pipeline()` downloads their prices in the same request as the companies' and runs `PriceAlert` on `screened + funds`; they skip the screener, the analyst rule and the profiles. They travel on `Snapshot.funds`, their rows land in `price_all` / `price_alerts` next to the companies', and `companies.json` marks them `asset_type: "fund"` so the cards hide the target, fundamentals and profile. Their names are hand-written rows in `data/tickers.csv` with sector "Fund" (`scrape_tickers.py` keeps rows it did not fetch). What each fund holds (`get_fund_details()`: TER, top ten holdings, sector weights, all in percent) is fetched every run onto `Snapshot.fund_details` and exported as `fund` on its `companies.json` row; `FundComposition.tsx` draws it. Yahoo publishes only the top ten holdings, so the list covers a quarter to a half of a fund. **The split by country is not in Yahoo**: `scripts/fund_countries.py` reads it from justETF's public ETF pages (by ISIN, listed in the script) into `data/fund_countries.json`, run by hand because scraping a third-party page from the daily job would break the run the day the page changes. `DataProviderImpl.get_fund_details()` merges that file in, with its `as_of` date, which the panel shows.
- **Ingestion scripts** (`src/scripts/`): run manually to refresh `data/`. Not part of the main flow.

## Frontend architecture (`web/`)

- **Charting libraries stay encapsulated**: `DataGrid.tsx` is the only file that imports AG Grid; `Chart.tsx`, the only one that imports ECharts. Pages only use `<DataGrid>` and `<Chart>`. Switching library = touching one file.
- **`lib/` is the boundary with the data**: `types.ts` mirrors the columns Python exports; `data.ts` concentrates the `fetch` and the `useData` hook. If the data ever comes from an API, only `data.ts` changes.
- **Numbers are formatted in one place**: `lib/format.ts` holds the rounding (one decimal everywhere), `formatCompact()` for money (44.3B) and `variationStyle()`, the green/red gradient. The gradient scale is FIXED and saturates at ±20%, so the same percentage paints the same colour across tables, cards and chart, and between runs. Change the scale there and every view follows.
- **Green and red mean price movement, and only that**: fundamentals are rendered neutral (`.stat`, not `.metric`). A debt ratio has no up-is-good direction, so putting it on the same colour scale would mislead.
- **The fundamentals shown, and their labels and units, live in one array**: `FUNDAMENTALS` in `components/CompanyCards.tsx`. The cards lead with the first three, which are the ratios the Python screener filters on. The prose sections of the profile are declared the same way, in `PROFILE_SECTIONS` right below it.
- **The price chart holds one series and slices it**: `PriceHistory.tsx` downloads five years once and each range button (3M / 1Y / 5Y) only decides how much of that array is drawn, so switching range never costs a request.
- **The detail panel freezes the page behind it**: it sets `body { overflow: hidden }` while open and restores whatever was there on close, so the wheel scrolls the panel rather than the list of cards underneath.
- **Three views over `companies.json`**: Summary (`/`), Analyst alerts (`/analyst`) and Price drops (`/price-drops`) all read the same file and keep only the rows whose rule fired (`analyst_alert` / `price_alert`). Filtering and ranking is `rankCompanies()` in `lib/filters.ts`, and every filter lives in the URL query (`?sector=...&min=15&window=var_1m`) so a reload or a shared link keeps the view. A minimum is a positive number meaning "down at least that much"; the rule's own threshold is already applied in Python, so the buttons only make it stricter. `CompanyCards` paints rows in the order given and takes the badges to show from the page, the first one drawn larger.
- **Search filters everything by hand** (`routes/SearchPage.tsx`): type, sector, minimum gap to the analyst target, window and minimum drop work as on the alert pages, except that "Any" means no filter at all. The fundamental filters (a min and a max each) are listed in `RANGE_FILTERS` and the table's fundamental columns in `FUNDAMENTAL_COLUMNS`; both take their label, unit and the plain-words text behind each `InfoTip` from `lib/metrics.ts`, so a filter and a column cannot disagree. They apply to stocks only, so setting any of them hides the funds; a `positiveOnly` metric (PER, price/sales) also drops values at or below zero, so "PER up to 15" does not return loss-makers. Results are a `DataGrid`, and a row click opens the same `CompanyDetail` panel the cards open.
- **Number boxes take a comma or a point**: they are text boxes with `inputMode="decimal"` read by `parseDecimal()` (`lib/filters.ts`), because the browser's `type="number"` follows the system language and refuses one or the other. The grid's number filters do the same through `allowedCharPattern` / `numberParser` in `DataGrid.tsx`.
- **`DataGrid` columns declare intent**: `numeric: true` gives a number filter (greater than, between...) instead of the text one ("contains"); `info` puts an `InfoTip` in the header. `InfoTip` draws its box in a portal under `<body>`, because a grid header clips anything that overflows it.
- **Pages (`routes/`) know neither where the data comes from nor how a grid is painted**: they declare columns, call `useData` and compose.
- **One breakpoint, 640px, in two places**: the `@media` block at the end of `index.css` (paddings, badges per row) and `NARROW_WIDTH` in `lib/useIsNarrow.ts`, the hook for what CSS cannot decide (how tall a grid or chart is, which columns exist). Everything else adapts on its own through `auto-fill`/`auto-fit`. If the breakpoint moves, both must move together.
- **A column can declare itself `secondary`**: `DataGrid` drops those columns below the breakpoint and caps the width the rest ask for, so the table fits a phone without sideways scrolling. Pages declare the intent; the responsive logic lives in `DataGrid.tsx`.
- **New page**: a file in `routes/` + a `<Link>` and a `<Route>` in `App.tsx`.
- **New column**: add it to the DataFrame in Python → to the type in `types.ts` → to the page's column array.
- **HashRouter**, not BrowserRouter: GitHub Pages returns 404 when reloading normal routes.
- **The dashboard is published to GitHub Pages by the same daily job that sends the email** (`.github/workflows/schedule.yml`): `main.py` writes `web/public/data/`, Vite copies it into `web/dist/` and that directory is the Pages artifact. It is one job on purpose -- the JSON exists only inside that runner, so building in a second job would publish a site with no data. The site is public, so the repository is too. Nothing in the frontend knows the repository name: `base: "./"` and the relative `DATA_URL` in `lib/data.ts` resolve against whatever path the site is served from.

## Conventions

- **Everything in the repository is written in English, with no exceptions**: variable, class and function names, comments, docstrings, log and error messages, commit messages, documentation, the text the user sees on the web (titles, column `headerName`, loading and error messages), URL routes, and the alert email.
- Type hints on every function signature.
- Imports relative to `src/` (not absolute from the repo root).
- Paths to data files use `Path(__file__).resolve().parents[N] / "data"` so they are independent of the working directory.
- The frontend code must be simple, and explained well enough for someone who knows nothing about React, TypeScript, Vite or web development. When you use one of those features, explain it at the top of the file or function in a comment. For example, if you use a React hook, explain what it does and why you use it.

## Environment variables

Backend — defined in `.env` (local) or GitHub Secrets (CI). Note that a variable
already present in the shell environment wins: `load_dotenv()` does not override it,
so a key can work locally without appearing in `.env` at all.

- `GMAIL_USER`: Gmail address used to send
- `GMAIL_APP_PASSWORD`: 16-character App Password
- `ALERT_TO`: alert recipient (optional, defaults to GMAIL_USER)
- `GEMINI_API_KEY`: key for the `gemini/*` models used by `utils/llm.py`
- `LLM_MODEL`: overrides the default model (optional, e.g. `ollama/gemma3:1b`)
- `LLM_MIN_INTERVAL`: seconds between two LLM calls (optional, defaults to 12.5).
  The free tier of `gemini-3.8-flash` allows **5 requests a minute and 20 a day**,
  so `utils/llm.py` spaces calls out and waits out a per-minute 429 instead of
  leaving the page textless. Set it to 0 with a local model, lower it on a paid key.
- `PROFILES_DIR`: see below. Pointing it at a scratch directory is how a profile
  run with another model is tried out without touching the real cache.
- `HISTORY_DIR`: where the Parquet archive is written (optional, defaults to
  `history/` at the repo root; CI points it at the checked-out `data` branch)
- `PROFILES_DIR`: where the cached company profiles are kept (optional,
  defaults to `profiles/` inside `HISTORY_DIR`, so CI commits them with the
  archive and the next run does not pay for them again)

The frontend does not need environment variables for now.

## Dependencies

Backend:
- `yfinance`: market data (price targets, fundamentals, statements)
- `pandas`: DataFrames throughout the data flow
- `requests`: Wikipedia scraping (index tickers)
- `python-dotenv`: loads `.env` locally
- `litellm`: one API for every LLM provider (Gemini, local Ollama, ...)
- `pyarrow`: Parquet engine behind the run archive

Frontend:
- `react` + `react-router-dom`: UI and routing
- `ag-grid-community` / `ag-grid-react`: tables (free version, MIT). No pivoting or row grouping: those are paid Enterprise features. If they were ever needed, the only change is the `registerModules` call in `DataGrid.tsx`.
- `echarts`: charts
- `vite` + `typescript`: build and typing
